### Proposed safe reset/purge protocol — DESIGN ONLY; owner approval required

The current frozen Settings clearMediaAfterReset() ignores sweep's result and removes local files except stashed refs. An arbitrary offline device cannot prove that an unreferenced hash is disposable. A finite grace period, logout, current state, device silence, or a successful backup download alone is NOT authorization. Observation-only sweep and truthful quota remain the local default; do not release until reset semantics and disclosure are resolved.

1. Separate user-visible operations: reset state while explicitly retaining server media (report retained count/bytes and resulting quota; verify local-only data and stash protection before wiping), and irreversible erase (existing authorized account deletion can erase the whole account, including media). A future selective purge must be a distinct, explicit owner action, never an implicit sweep/reset. No claim that reset has erased server media; no automatic deletion merely to recover quota.
2. Read-only preview under the media/state admission gate: authenticate, read a valid committed revision/generation, bound inventory, compute exact owner-scoped candidate hashes/sizes/ETags, referenced/retained counts and plan digest. Fail closed for unreadable state, inconsistent inventory, busy gate or mismatched owner. No R2 mutation. The current sweep validates only observation/counting, not this future full preview contract.
3. Preserve/recover path: verify an independently stored encrypted export of state plus all required bytes (hash, size, manifest integrity), demonstrate restore against disposable local resources, and explicitly identify missing/oversized/sole-device data. Any unknown offline references remain an unresolved risk. For a true privacy erasure request the owner must explicitly choose irreversible loss and deletion of applicable backups; a backup is not mandatory for an intentional erasure and must not silently defeat it. Never claim all disconnected copies were erased remotely.
4. Separate step-up owner authorization bound to exact plan, revision, account generation and expiration; explicit scope and consequence acknowledgement. Require a fresh preview if state, references, object metadata or session changes. For selective purge, design generation fencing and stale-client rejection/reconciliation (including intentional restoration with new authorization) before deletion; do not promise old installed clients understand new semantics. Session revocation, active/offline device behavior and local reset disclosure need separate acceptance. Account deletion remains existing independent authorized path.
5. If approved later: durable SQLite intent/tombstone before R2 IO, disable conflicting operations, bounded <=16 keys per recovery, verify absence of every target and never delete new or foreign objects. Retry idempotently after partial success, lost ack, crash and restart; do not report completion until durable finalization. No unauthenticated intent creation. Recovery/restore must use exact verified manifest and generation checks. Never silently restore intentionally erased data.
6. Qualification before owner approval: preview nonmutation, unauthorized/stale plan/foreign scope rejection, unreadable state and changed ETag refusal, re-reference/racing uploads, bounded quota and full-inventory behavior, interruption/partial success and rollback, stale-device resurrection prevention, backup restore and explicit erasure distinctions, honest UI and installed-client compatibility. Only the current retention/quota/account-delete invariants are tested or queued in HF006; selective purge protocol itself is not implemented/accepted.

Recommendation: verify HF006 first; resolve legacy acknowledged-copy pending gap with safe migration design, choose reset/erase UX and selective purge policy with owner, and only then implement approved non-destructive preflight/reconciliation or destructive intent protocol under separately authorized scope.
