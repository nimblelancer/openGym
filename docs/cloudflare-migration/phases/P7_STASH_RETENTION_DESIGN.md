## 3. Proposed versioned model (not code)

Keep legacy raw files untouched by new automatic adoption/cleanup: gym_stash and opengym-stash.json. Keep web legacy path unchanged initially; any migration of synchronous web writer is separate and must preserve existing fail-closed owner switching. Design a private, versioned record namespace, e.g. opengym-stash-v2/ for native and separate gym_stash_v2:* keys for browser. The names are proposals, not an installed capability or approved format. Never add a fake UID or receipt into the legacy inventory.

Each immutable record has schema/version, type, independent publication ID (cryptographically random, at least 128 bits; prefer 256), exact server namespace (normalized according to existing pairing identity including subpath, never silently collapse distinct origins), owner UID, entry kind (owned, held adoption, active-only, manual/device-only, legacy-unbound), full validated payload including active and unknown supported fields, timestamp as diagnostic/order input only, source reference and SHA-256 over versioned canonical serialized entry. Define canonical encoding explicitly before implementation: deterministic sorted object keys, preserve array order, JSON-safe finite values, reject duplicate/invalid keys and unsafe integers, bounded depth and size, no implicit Unicode or URL equivalence, domain-separated SHA-256; hash original raw UTF-8 bytes separately for byte-preservation inventory. If digest matches, verify exact canonical bytes before dedupe. Same key/at with divergent digest remains distinct; preserve same-owner newer and older divergent payloads and all foreign/device-only variants. Keep raw legacy bytes (and snapshot if an independent immutable copy is required before later reliance); unknown or malformed entries are held, not discarded or silently normalized. Never claim a newer timestamp subsumes all edits. Manual/device/null-server records cannot be automatically bound to arbitrary new account/server; explicit user decision or existing proven owner continuity required.

Receipt is a separate immutable record, not a mutable index or tombstone:
schema, receipt ID, kind, record IDs and exact per-entry digests, bound owner and server, attempt ID, submitted wire-byte digest, accepted response rev/wid, verified committed rev/wid and canonical client-visible committed digest, merge disposition evidence, local active/media durability proof reference, receipt version. Never persist bearer, cookie, passkey, credential or full HTTP headers. ACK intent and resolution records are separate from originals. No receipt for only an owner key, a timestamp, generic sync flag or local merge result. No global mutable 'consumed' pointer. Receipt is local evidence, not a signature or permanent server generation proof.

Publication protocol: allocate unique unused namespace per record; capability test actual adapter allocation/no-clobber, directory inventory, direct read and error semantics before trusting it. Random naming + no shared index reduces cooperative collisions, not absolute exclusion against arbitrary writer or malicious same-path write. Never reuse/overwrite existing record even after a failed write; on collision/ambiguous read stop or allocate another unique ID only if original retained. Write exact bytes, strict readback, compare full bytes/hash/schema, recheck owner/session/live state before any transition. Independent native and browser record copies can differ in physical publication IDs but carry identical logical digest; require positive durable verification of at least one medium before existing permitted transitions (one-medium recovery must be qualified), both where mandatory contract requires. Do not clear source/live state/credential or delete raw copy to make room. A failed/partial record is visible as incomplete and must block destructive decisions. No shared manifest whose replacement could lose records; enumerate all records and legacy sources. Missing namespace vs unavailable/malformed enumeration distinguished. Resource bounds cause HOLD, never truncated 'complete' inventory. Verify exact-read capability and directory discovery including restart and orphan partial files. No fsync/exclusive-create guarantee assumed from JS API; crash persistence/OS termination remains physical gate.

## 4. Adoption and acknowledgement state machine

READ/INVENTORY -> VALIDATE -> MATCH/PLAN -> DURABLE INTENT -> CONDITIONAL PUSH -> AUTHORITATIVE READBACK -> RECEIPT PUBLICATION -> LOGICALLY ACKNOWLEDGED (raw retained). Any ambiguous step -> RECOVERY REQUIRED/HOLD (raw retained).

1. Inventory both legacy media separately, immutable entries, intents/receipts, live state and both native mirrors. Keep raw-retained view separate from pending view; never auto-adopt foreign or unbound unknown-server state. Derive deterministic list of exact eligible entry identities, not a merged key digest. Apply existing merge/stamp/reset/unit semantics, preserve both active candidates if divergent, and do not push raw manual-only state. Record plan and state version under same owner/session; ensure original bytes durable before requesting transition.
2. Persist and verify intent before network attempt (records, submitted payload identity, baseRev/baseWid, owner/server, attempt ID, local active/media obligations). Failed intent persistence => no automatic adoption PUT and no destructive transition; report recovery hold. Preserve old source. Do not write an intent into state S or API payload. If state changes while hashing or publishing, invalidate plan and replan without changing old record.
3. Instrument doPush per actual attempt (proposed internal return/event, no external API contract change yet): exact serialized PUT bytes, current token/owner/server, base rev/wid, response, conflict outcome. Bind only the attempt that really incorporated the planned merge and passed current authority. A 409/rebase creates a new plan/attempt; prior intent stays unresolved, no receipt from failed attempt. No force replace solely for stash adoption. Missing wid/rev, 200 without valid ok, stale session, auth failure, non-current owner, new owed state => no authoritative receipt. Existing server compatibility without wid remains pending/manual recovery, not a fabricated ACK.
4. GET /api/me and /api/data under same current authenticated session and verify owner and server identity, ACK wid == authoritative state's _wid, committed revision from readback (not assume ACK rev equal; permitted stamp increment verified), canonical committed digest, required disposition of each exact input under existing merge/reset/tombstone policy. Verify reset/intent semantics without requiring stale deleted content to reappear. No generic subset/ID-only equality: validate values, edits, tombstones, all relevant fields and intentional conflict resolution; ambiguous transformation or an intervening write before exact readback => no final receipt, reconcile. Distinct submitted-wire and committed-state digests; exact projection/comparator to be specified and tested against transition and upstream, not silently ignore unknown fields. Local active and media obligations independent of server state (server strips active); do not mark fully consumed until owner-tagged exact active durability or explicit resolution and referenced original media preservation verified. Active-only record cannot be treated as server-acknowledged merely by an empty PUT. Avoid duplicate completed active workout restoration; if consumption evidence is missing or conflict exists, hold for explicit recovery.
5. Publish receipt independently with exact readback and current authority check. Never call writeStashes, native overwrite, tombstone or compaction for automatic adoption. Intent/receipt may be partial/duplicated; dedupe only exact validated identity. On same-authority restart, a valid receipt suppresses ONLY that exact entry in pending view; original remains exportable. Newer/divergent entries have different identity and remain pending/recovery candidates; foreign remains owner-isolated. If same entry is observed as a stale legacy copy, don't merge it again while valid receipt authority holds. A new deliberate preservation event may contain previously acknowledged records; preserve actual new event and merge by current state/reset policy, not blanket suppress by old digest. No receipt can authorize deletion or hide raw media refs.
6. Restart/rewind: require fresh authority before automatic adoption of records that could have been acknowledged. Current exact wid + rev + digest is strong scoped evidence; descendants with same trusted server generation may be accepted only under a separately qualified lineage contract. _wids last 50 or same revision alone cannot prove generation, especially restored server with identical state. Missing/expired lineage, same rev different wid, changed owner/server, restored identical snapshot with unknown generation, lost ACK, missing/malformed receipt, unavailable auth or unreadable storage => RECOVERY REQUIRED, do not auto replay or silently mark resolved. Reconcile with current state and user-authorized recovery; no automatic resurrection of reset/deleted work. A lost receipt plus lost intent is indistinguishable from never attempted legacy stash; cannot guarantee both seamless automatic adoption and no resurrection. Conservative hold on ambiguous legacy/import/receipt loss is a behavior change requiring explicit approval; full no-resurrection across arbitrary device/metadata loss is unproven. Do not claim current API provides permanent authoritative epoch/idempotency.

Views: proposed pending view powers existing keptChanges/keptState semantics for unacknowledged entries (exact acknowledged can return null logically). Add separate raw retained inventory/export by record ID, owner-authorized recovery, explicit status (pending, acknowledged retained, ambiguous/held, corrupt/unreadable, manual-only). UI must report physical retention, not 'deleted'; no silent export omission or cross-account display/download. Existing UI consumer inventory and access control require implementation review; current shared-device recovery behavior cannot be silently changed. stashedMediaHashes must consume raw retained union including acknowledged entries, all versions/active/posters/device-only/pending, never pending view. Unreadable inventory aborts GC; pressure doesn't evict protected bytes. Until safe cross-process GC authority proven, hold potentially destructive eviction for uncertain retained media; reset hold remains.

## 5. Publication paths and compatibility

Proposed incremental mobile-only design: replace every v2 writer path (prepareMobileSwitch, stashOwed, stashActive, keepAside and any mobile keepForPrevious fallback) with per-record publication before switching, disconnect/signout or wiping. No whole-map merge-and-write. Snapshot live owner/session and all relevant versions, preserve separate new version and any divergent originals; return failure and retain current state if durability/authority changes. Keep existing public result shapes and no credential changes before verified stash. Audit best-effort keepAside callers, boot/adopt/reset/backup import and clearLocalSession before implementation. Existing synchronous browser keepForPrevious cannot await a native journal; keep web unchanged until separate design/approval, preserve quota fail-closed, do not falsely certify cross-tab atomicity. Mixed legacy/new client access to same device files must be prohibited or explicitly qualified; legacy still can overwrite its legacy map and does not discover new-only records. A dual-write to legacy map reintroduces the confirmed risk, so not a safe compatibility fallback. Independent publisher that only writes legacy file can be preserved during new automatic adoption because v2 never mutates that file; unknown arbitrary external writers or old clients can still delete/overwrite legacy sources. No universal guarantee. Source-only feasibility does not provide official installed client support; determine actual supported update path/version and prove Android/iOS behavior before release. If mandatory unchanged official app cannot consume v2, owner must choose separately authorized native/client release or stop migration.

Quota/privacy: account records may contain full exercise/health history. Proposed byte/count/time budgets measured separately for localStorage/native incl receipts and partial records; reserve headroom before transition, stop with explicit recovery/export guidance on capacity, never automatically purge. No chosen limits without measurements/approval. Read-only inventory cannot rely on limited list as completeness. Measure Android backup cap implications and iOS backup exposure; encryption/key custody, device migration, backup/export format and shared-device access require design/physical gates. Don't claim private directory is encrypted or off-provider backup. No state/receipt digests or PII in CI logs beyond synthetic IDs/booleans/counts. Do not expose records in ordinary synced state.

Explicit deletion: separate irreversible owner-authorized workflow from ACK. Existing server delete then shared-map clear is not suitable for uncoordinated retained inventory. Do not execute or change it in design iteration. Proposed preflight enumerate exact owner/server originals, receipts, intents, mirrors, backups and shared media references; distinguish foreign data and retention legal/privacy obligations; verified authority, explicit confirmation, per-record erase only with safe coordination/capability and proof, no delete-all/legacy map overwrite. If cannot ensure safe targeted erase or privacy promise, report incomplete and block claiming deletion completed; server/session deletion and local retained privacy obligations tracked separately. No use of reset/GC for deletion; no destructive purge authorized. Retained backup copies/key custody remain independent obligations.
